### P-09 추가 제안

```
P-09  zc24 전환 상태에서 원복 → 기존 클러스터로 1회 실행 → 재전환
```

## 4. 해결되지 않은 사항

코드로 막을 수 없어 **운영 판단이 필요한** 항목입니다.

### 4-1. 키 볼륨의 노출 범위

원본 YAML 은 `path: /batch_gke/l2/rsvp` 를 통째로 `/var/run/bq-key` 에 마운트합니다.
`readOnly: true` 가 훼손은 막지만 **그 디렉터리의 다른 업무 파일까지 zc24 파드에
노출**됩니다.

- NFS Export 가 허용한다면 키 파일만 있는 하위 경로를 쓰십시오
- 불가능하면 이 노출 범위를 보안 담당자에게 고지한 뒤 진행하십시오
- 운영에서는 Kubernetes Secret 으로 옮기는 쪽이 맞지만 변경 최소화 원칙과 충돌합니다

### 4-2. 이미지 digest 와 실제 코드의 괴리

사용자께서 구상하신 "AR 이미지 + 개발 py 를 파드에서 머지" 방식을 채택하면,
`kubectl describe pod` 의 digest 는 런타임 껍데기만 설명합니다.

- `kubectl rollout undo` 로 되돌려도 볼륨 내용은 그대로
- 장애 분석 때 "그때 무슨 코드가 돌았나"를 digest 로 추적 불가
- AR 취약점 스캔은 베이스 이미지만 검사

최소한의 장치로 코드 리비전 어노테이션을 권합니다.

```yaml
annotations:
  code-revision: "${REV}"
  git-commit: "$(git rev-parse --short HEAD)"
```

### 4-3. Wave 전환의 실효성

라우터를 배치하지 않으면 10.3 의 모순이 그대로 남습니다. 전체 Cron 을 곧바로
열면 Wave 구분은 무의미해지고, 30개가 한 번에 신규 클러스터로 향합니다.

라우터를 쓰지 않기로 하셨다면 **업무별 Cron 순차 재개 절차를 문서로 확정**하고
담당자·시각·순서를 못박아 두셔야 합니다.

### 4-4. 일정 현실성

D-5 부터 D-1 까지 하루에 한 단계인데, IAM 권한 부여와 Shared VPC 방화벽 변경은
보통 하루에 끝나지 않습니다. 13장 분장표의 담당자가 전부 다릅니다.

- D-10 전후에 권한·방화벽 요청을 **전부 동시에** 제출
- D-5~D-2 테스트는 권한이 도착한 순서대로 병렬 수행
- 파일럿을 1회가 아니라 **정기 스케줄로 연속 3일** — 1회 성공은 재현성을 보장하지 않습니다
